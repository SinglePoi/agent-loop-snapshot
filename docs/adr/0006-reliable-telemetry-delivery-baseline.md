# ADR-0006：可靠遥测交付 v2 基线与迁移

- 状态：已接受
- 日期：2026-09-16
- 关联任务：TDX-00 至 TDX-06
- 取代范围：补充并在可靠交付语义上取代 ADR-0005 的状态、版本和队列恢复约定；ADR-0005 的独立包边界、显式目的地、出站过滤早于持久化、禁止递归采集及“不承诺 exactly-once”继续有效。

## 背景

ADR-0005 的 `otel-export-1.0` 已交付纯映射、HTTP 客户端和队列原型，但复核发现其状态码、重试尝试配对、出站元数据过滤、目标绑定和单锁发送语义不足以作为可靠交付契约。不能通过在旧 JSON 上猜测字段含义来修复历史条目；那会把可能已按旧错误编码生成的数据误发到新目的地。

## 决策

### 版本与兼容

`otel-export-1.0` 保持为现有实现和既有 TypeScript 消费者的版本。可靠交付的目标契约固定为：

| 项目     | 固定值                    | 用途                                |
| -------- | ------------------------- | ----------------------------------- |
| 交付契约 | `otel-export-2.0`         | 工厂、CLI 与汇总交付报告            |
| 映射     | `otlp-json-mapping-2`     | span 配对、OTLP wire 编码与过滤语义 |
| 队列     | `otlp-persistent-queue-2` | 持久化条目、租约和恢复状态          |
| 编码     | `otlp-http-json`          | 首版线上 OTLP/HTTP JSON             |

TDX-01 至 TDX-05 完成前，不得将 v1 发送器、队列或报告标记为 v2 合规。公共 API 在迁移期间保留 v1 类型；新增 v2 报告使用聚合结果与逐批次结果，避免一份快照拆批后只返回一个看似完整的状态。

不能明确标识为 `otlp-persistent-queue-2` 的旧队列条目必须隔离，不自动发送，也不通过观察整数状态码修复。诊断应要求从仍受用户明确授权的源快照重新导出。v2 队列条目必须携带映射、过滤策略、编码和队列版本。

### 目的地、凭据与配置

每个 v2 批次绑定用户提供的 `targetAlias`、安全可持久化的 `destinationIdentity` 与显式 `destinationGeneration`。身份值不得是 endpoint URL、header 或凭据，也不得由凭据哈希推导。凭据可轮换；切换租户、Collector 或授权域时，用户必须改变目标身份或代次并重新导出。

配置优先级固定为：显式 API/CLI 配置优先于配置文件；本阶段不读取标准 `OTEL_EXPORTER_OTLP_*` 环境变量。仅 endpoint/headers 的环境变量引用可在发送时解析。`timeoutMs=0` 在 v2 中无效；timeout、总预算、容量与重试次数均须为有限正整数。标准环境变量和零值兼容策略留给 TDX-10 的独立 ADR。

### 交付状态与报告

v2 的规范状态为：

| 状态                     | 含义                                                       |
| ------------------------ | ---------------------------------------------------------- |
| `not_sent`               | dry-run、无数据或尚未提交发送意图，不代表远端成功。        |
| `configuration_blocked`  | 缺少凭据、目标不匹配或配置无效；可恢复工作必须保留。       |
| `pending`                | 已登记/入队，尚未获得远端接受结果。                        |
| `accepted`               | 接收方完整接受。                                           |
| `accepted_with_warnings` | 接收方接受，且 `partialSuccess` 拒绝数为零但有安全诊断。   |
| `partially_rejected`     | 接收方明确拒绝了一部分；不得自动整批重发。                 |
| `permanently_rejected`   | 接收方明确且不可重试地拒绝。                               |
| `retry_scheduled`        | 暂时失败，持久化 `nextAttemptAt` 后等待。                  |
| `retry_exhausted`        | 重试/预算耗尽，保留待处理证据。                            |
| `unknown_delivery`       | 请求可能已送达但结果不可确认；后续人工或受控补传可能重复。 |

批次报告包含接受/拒绝数、累计尝试数、下次尝试时间和经脱敏的诊断。快照级报告必须列出每个批次、pending span/batch 总数以及 unknown-delivery 数；排队、远端接受和平台 UI 已索引是不同事实。

### 队列恢复与测试基线

TDX-04 将以独立生产者短锁与带 owner token/续租的消费者租约替代 v1 的单一发送锁。网络 I/O 不得持有生产者锁。持久化恢复状态至少包含首次尝试、累计尝试、最后结果、`nextAttemptAt`、回执和版本化批次身份。所有 pending、待处理、隔离和临时文件都纳入容量与保留期限。

从 TDX-00 起，根测试与打包消费者 smoke 必须加载并执行 `@agent-loop-snapshot/otel-export`。后续每项行为修复先加入能捕捉旧行为的回归用例，再改变实现；TDX-07 另行增加固定版本 Collector 的真实解码验收。

## 后果

- 现有 v1 API 在迁移期可继续编译，但不获得 v2 可靠交付声明；
- 后续任务可根据固定的 v2 状态、版本和报告形状独立实现，不需要重新定义队列语义；
- 用户在升级后可能需要从源快照重新导出未版本化旧队列，而不是继续自动补发；
- 本 ADR 不授权上传历史快照、部署 Collector、变更外部账号或发布包。
