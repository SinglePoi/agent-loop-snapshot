# 遥测可靠导出、本地查看与后续演进开发计划

日期：2026-09-16。状态：待实施，供 coding agent 执行。

本文汇总社区方案对比、当前实现复核和改进建议。本文中的任务均为待办；讨论中已完成的排查和样例复现不代表功能修复已完成。

## 1. 目标与阅读方式

目标是让用户可靠地完成：记录 Agent 运行、本地排查、选择允许上传的内容、发送到观测平台、断网或重启后补传，并逐步获得本地查看界面。

大白话：任务跑过以后，既有一份留在自己电脑上的档案，也能把允许分享的部分送到平台；平台看到的成功、失败、重试和耗时必须准确。

本文有三个独立交付阶段：

| 阶段            | 任务             | 交付结果                                              | 执行边界                                            |
| --------------- | ---------------- | ----------------------------------------------------- | --------------------------------------------------- |
| A：可靠导出闭环 | TDX-00 至 TDX-07 | 修正映射和发送队列，接通 SDK/CLI，完成 Collector 验证 | 默认执行范围，承接原 EXP-05/06，并补强 EXP-02/03/04 |
| B：本地只读界面 | TDX-08           | 可浏览本地 Snapshot 的 Viewer                         | 独立交付；显式执行 B 或整份计划时实施，可与 A 并行  |
| C：后续能力     | TDX-09 至 TDX-12 | 语义互通、更多传输、实时关联、成本和性能控制          | 按指定任务实施；不作为 A 完成的前置条件             |

交接时只说“按本文实现”，默认完成阶段 A。说“实现 A+B”则包含本地 Viewer。说“实施整份计划”则依次完成 A、B、C；外部账号、生产部署和公开发布仍按第 11 节边界处理。

每个任务包含“大白话作用”“实施要求”和“验收标准”，可直接拆成 Issue 或提交。任务编号 TDX-* 表示本次增量，不重用已有 ALS/CAP/EXP 编号。

## 3. 已确认的问题与建议修正

### 3.1 已确认的实现问题

1. **OTLP 状态码错误。** `mapper.ts` 的 `toOtlpSpan()` 将 OK/ERROR 编为 2/3；官方 wire enum 为 UNSET=0、OK=1、ERROR=2。必须测试最终请求字段，而非只测试内部字符串。
2. **重试历史被覆盖。** `mapNativeOrSdk()` 的 calls/finishes 按 `correlation_key` 保存单条记录。同一逻辑调用的多次尝试会互相覆盖。使用 `packages/schema/fixtures/tool-failure-retry` 复现：两次 tool.requested、一次 tool.failed 最终只导出一个成功工具 span，开始时间来自第二次请求，损失报告未指出重试丢失。
3. **元数据出站过滤不完整。** resource 的 `service.name`、scope 名称/版本、部分关联字段直接进入输出。metadata-only 不等于任意字符串安全；需统一经过允许列表和出站限制。
4. **目标指纹只绑定环境变量名。** endpointEnv 对应值变化时，配置指纹可能保持不变，无法保证旧批次仍绑定原目标。
5. **发送持锁影响生产者。** enqueue 与 flush 共用锁，flush 持锁执行网络调用；发送期间新数据可能返回 not_queued。锁仅按 mtime 回收，缺少续租及所有权保护。
6. **交付状态与预算边界不完整。** partialSuccess 拒绝数为零也被分类为 rejected；总预算未限制下一次请求的实际可用时间。队列累计 attempts 未形成跨 flush 的统一重试调度。
7. **入口与自动门禁尚未闭合。** 导出工厂、SDK/CLI 接入待做；根测试清单在复核时没有执行 otel-export 测试。batchSpanLimit 只有配置定义，缺少实际拆批。

以上为 2026-09-16 的检查结果，执行者应先在当前源码确认，再增加能捕捉问题的回归用例。不要直接沿用旧行号。

### 3.2 对此前建议的修正

- HTTP JSON 是合法 OTLP 编码；阶段 A 保留 ADR-0005 的选择。protobuf/gzip/gRPC 不应一起成为首轮交付前提。
- 项目自定义 `timeoutMs=0` 的意义必须明确，不能未经约定就套用某一 SDK 的默认行为。阶段 A 建议要求有限正整数超时；后续标准配置适配必须单独说明零值转换。
- Viewer 已在 ALS-204 中规划，依赖读取和图投影，不依赖上传；可独立并行实施。
- Collector 接收成功不代表所有云平台的界面都能正确展示；稳定 ID 也不保证所有后端自动去重。
- 本地全量留存必须有明确范围和容量政策；需要回放的快照不能随机删除内部事件。
- 哈希与结构校验支持完整性排查，不构成不可篡改的可信审计证明。任意代码调用栈、未记录的变量和历史授权不能从 Snapshot 自动恢复。

## 4. 统一工程约束

1. 记录失败、业务失败、导出失败分别报告。导出失败不得重跑模型/工具，不得改变业务返回值或把已完整记录的快照降级为采集不完整。
2. Recorder/schema/replay 不反向依赖网络导出实现。通过轻量接口连接采集层和可选 exporter；避免循环依赖。
3. 不替换或关闭应用已有 OTel provider/context manager/exporter。导出自身网络请求不得递归生成本项目遥测。
4. 默认 metadata-only；正文必须显式开启，出站过滤必须早于队列、临时文件和报告持久化。凭据只在发送时读取，不进入快照、队列、命令行、日志或报告。
5. 目的地由用户配置；快照中的 URL、脚本、路径和授权声明都是数据，不是执行指令。保留现有路径边界、常规文件检查、读取限额和 observation-only 门禁。
6. 不承诺 exactly-once。默认有预算地补传允许重复；明确区分接收方确认、未知送达与界面已索引。
7. 更改映射、报告或队列持久化语义时，版本化相应契约并测试旧数据。尤其旧队列可能包含错误状态码，不能无版本判断地当成新格式发送。
8. 本文阶段 A 会调整 ADR-0005 的状态分类、锁和失败条目处理。TDX-00 应增补 ADR 或写明替代条款；保留设计变更来由，不静默修改历史约定。
9. 当前复核时工作区已有 README、CLI package、Trace 和 Replay 的未提交改动。执行前重新检查 git 状态和局部 diff，保留其他工作的内容。

## 5. 阶段 A：可靠导出闭环

### TDX-00：冻结契约、修订 ADR 和交付基线

**大白话作用：** 先说清哪些情况算成功、断网怎么补、旧记录怎么办，让各模块按同一套规则工作。

依赖：无。可行性：高。对应原任务：EXP-01 补充。

实施要求：

- 阅读现有采集计划、ADR-0004/0005、安全与发布指南；核对本次问题在当前版本是否仍存在。
- 固定映射版本、队列版本、批次/任务级报告形状、配置优先级、超时零值和升级策略。
- 一份快照可能拆成多个批次；调整现有只返回单个 ExportDeliveryReport 的接口，使其能报告总量、逐批次状态、部分入队和剩余工作。
- 旧队列不明确知道映射版本时，隔离并提示从源快照重新导出；不得按看似相同的整数盲目修复历史 payload。
- 将导出测试加入根测试入口，核对构建 references、依赖与 release smoke 清单。
- 固定输出状态至少表达：未发送/配置阻塞、待发送、已完整接受、接受但有警告、部分拒绝、永久拒绝、暂时失败待重试、自动重试耗尽、未知送达。具体枚举名写入 ADR，不要求照搬本文文字。

验收：契约文档与公共类型一致；旧消费者兼容性和升级行为有测试；能在根测试命令中看到导出测试执行。

### TDX-01：修正 span 映射与重试配对

**大白话作用：** 把任务过程准确翻译给平台，保留“先失败、后重试成功”的全部经过。

依赖：TDX-00。可行性：高。入口：`mapper.ts`、导出测试；对应 EXP-02 修正。

实施要求：

- 使用正确 wire enum；优先采用官方定义或集中类型常量，避免散落手写数字。
- 一个实际 requested 事件代表一次尝试。稳定 span ID 至少包含 run 与 requested 事件身份；同一逻辑调用可共享 correlation 属性。不能仅按 correlation_key 或参数去重。
- 配对优先依据同 run、调用类型及终态对请求的父引用；旧数据缺乏明确引用时使用确定且保守的匹配规则。存在歧义就诊断，不偷偷选择最后一条。
- 保留并行、嵌套、多父链接和失败历史；不把调用返回后的先后执行顺序自动解释成数据依赖。
- 检查重复导出稳定性、不同调用类型复用关联键、缺终态、错误终态、根时间区间和非法时间。
- 明确缺终态策略：阶段 A 不构造正常完成时间；无法形成合法 ended span 的调用进入损失报告并保留本地记录。若采用“观察截止时间”，必须另行定义字段，不能冒充真实结束时间。
- 深祖先遍历采用显式栈/队列，避免合法长链导致调用栈溢出。
- 核查 run 输入/输出和导入 resource/scope/links 的实际处理；有意过滤或无法保留的字段进入报告，不能承诺无损导出。

验收：重试 fixture 导出包含两次工具尝试，第一次 ERROR、第二次 OK；线上编码为 2/1；并行、跨类型同键、歧义、长链和重复映射用例通过。

### TDX-02：统一出站过滤与容量限制

**大白话作用：** 寄出的正文、标签和备注都检查一遍，同时避免一个超大结果堵住整个上传通道。

依赖：TDX-00；与 TDX-01 可并行设计，合并后联合验收。入口：mapper、公共类型与报告。

实施要求：

- 制定 metadata-only 字段允许列表；自由文本即使属于资源、scope、关联信息，也必须经过策略处理。
- 凭据样式识别不能替代正文显式授权；脱敏规则支持项目既有定制需求，默认规则与本地处理保持可解释的一致性。
- 关联键可使用稳定哈希保留关联能力；协议 trace/span ID、时间和状态字段不能被普通文本规则破坏。
- 默认不展开 artifact 内容，不发送预览和本地绝对路径；报告本身也必须脱敏，包括诊断路径和服务端返回消息。
- 限制字符串 UTF-8 字节、属性/事件数量、嵌套深度、单 span 与整个请求字节数；定义截断/拒绝规则与计数。
- 遍历输入时防止循环、深递归和危险对象键；无效输入产生受控诊断。
- SDK、CLI、dry-run、队列使用同一条过滤与拆批逻辑，防止预览与实际发送不一致。

验收：在模型正文、工具参数、service.name、scope、关联键、错误消息和 artifact 元数据中放入合成测试秘密，检查出站请求、spool、临时文件与报告；验证限额前就阻止无界物化。dry-run 不联网、不入队。

### TDX-03：修正发送响应、取消与重试预算

**大白话作用：** 区分“没寄出去”“对方只收了一部分”“回执丢了”，决定什么时候可以再试。

依赖：TDX-00。入口：`http-client.ts`；对应 EXP-03 修正。

实施要求：

- HTTP 200 的 partialSuccess 拒绝数为零且带警告时报告已接受并附安全警告；实际部分拒绝单独报告，不自动整批重发。
- 验证响应结构和拒绝数范围；无效 JSON/响应超限不能误报接受。发送后响应不可解释时保留未知送达信息，避免错误认定所有 span 都被拒绝。
- 发送前取消或缺凭据应报告未发送/配置阻塞，保留可恢复工作；不应被队列视为永久远端拒绝后删除。
- 保留 OTLP 定义的可重试 HTTP 状态、Retry-After、指数退避和抖动。网络断开或超时可能已送达，不能承诺重发不重复。
- 每次请求超时取配置上限与剩余总预算的较小值；退避不能越过总 deadline。时间预算使用单调时钟，HTTP 日期解析使用墙上时钟。
- 清理响应体、定时器和取消监听；配置数值做有效范围校验。
- 继续禁止自动重定向及隐式目的地；发送时鉴权可轮换，但同一待发送批次的目的地不得跟随环境变化漂移。

验收：覆盖完整接受、零拒绝警告、部分拒绝、非法响应、401/400、429/503、日期形式 Retry-After、断连、发前取消、发后取消，以及剩余预算不足的边界；绝不执行模型或工具。

### TDX-04：可靠队列、目标绑定与恢复状态机

**大白话作用：** 网络慢时还能继续存新记录，重启后知道哪些已经发了，哪些还需要处理。

依赖：TDX-00、TDX-02、TDX-03。入口：`queue.ts` 及新增内部存储模块；对应 EXP-04 补强。

实施要求：

- 指纹绑定规范化后的实际目的地身份、目标/租户路由配置、内容策略与策略版本、映射版本及编码。不得保存认证值或对密钥本身做可暴露的指纹。
- 相同鉴权变量换成另一租户凭据时，程序未必能识别；增加显式目标身份/配置代次的约定，文档说明用户跨租户切换须变更目标身份。
- 队列只保存目的地身份摘要，不保存含敏感参数的 URL。send 前验证当前目的地仍匹配；凭据轮换可用，目标改变需要显式重新导出。
- 采用短时元数据/生产者锁和独立消费者租约，或事务性存储。网络发送不得长期占用入队锁；容量判断与入队提交仍须并发安全。
- 租约带所有者 token、续租及安全回收；旧消费者不能删除新消费者的锁或确认其不再拥有的条目。跨进程测试暂停、崩溃、抢占和恢复。
- 持久化 nextAttemptAt、累计尝试、首次尝试时间、最后结果及重试预算；反复调用 flush 不能重置全局限制。
- 接受后更新回执；永久拒绝、部分拒绝及耗尽进入有界待处理档案，保留原因和源快照关联。取消自动重试与删除证据是不同操作。
- 对坏 JSON、未知版本、超限、临时残留进行隔离或安全清理，不能静默忽略且绕过容量统计。pending、待处理、隔离和临时数据均受容量/期限约束。
- 读取前执行大小和文件边界校验；明确 file sync、原子发布和目录持久化的跨平台保证，不把进程崩溃恢复等同于所有断电场景保证。
- 暴露 pending 数/字节、最老条目年龄、拒绝/过期/耗尽/未知送达数量；指标标签不带 run ID 等高基数字段。

验收：本地多进程测试验证发送慢时仍能入队、无容量越界、租约过期后所有权安全、目标环境变量改变不串写、凭据缺失不丢批次、重启保留退避预算、损坏文件可诊断。

### TDX-05：导出工厂、稳定拆批和快照到队列的恢复

**大白话作用：** 把“转换、检查、分包、存队列、发送”组装成一个可以直接调用的工具，并补上存档后突然退出的空档。

依赖：TDX-01 至 TDX-04。入口：otel-export 新工厂、批次与交付记录模块；承接 EXP-05。

实施要求：

- 实现 createOtlpExporter(config)、exportSnapshot、flush、shutdown；工厂初始化与资源所有权有明确契约。
- 按 span 数和编码后字节拆批，保持 resource/scope 分组、稳定顺序和关系 ID。单 span 超限单独诊断，不允许无限重试一个永远发不出的请求。
- 稳定批次身份绑定快照内容/修订、目标、映射、过滤策略与拆批参数。重复提交相同批次可幂等入队；这仅保证本地去重，不保证后端 exactly-once。
- 交付记录存于独立目录，不改写源快照来表示上传结果。记录各批次创建、入队、确认和待处理状态；批次 payload 与回执提交顺序可恢复。
- SDK 只对显式启用导出的 run 建立交付意图。持久化意图或受控范围索引，补齐“快照已提交、还没入队”就崩溃的恢复路径。
- 补传只扫描显式授权且已经启用导出的范围，不扫描整机或自动发送历史导入快照。未完成或未提交快照保留诊断，不能自动伪造完成状态。
- 已接受批次的回执保留期限应与自动恢复扫描窗口协调；明确过期后人工重新导出可能重复。容量/写盘故障导致无法保存意图时，报告无法保证自动恢复并保留源快照。
- shutdown 停止接收新任务，以有限 deadline 收尾；重复调用返回一致终态。flush 可继续使用，但不能创建多个争抢的发送循环。

验收：在快照提交后、入队前、部分批次入队后、发送确认前后、回执提交前后注入进程中断；恢复后无静默漏发，未知送达明确提示可能重复，稳定拆批和内存上限可验证。

### TDX-06：SDK 生命周期与 CLI 导出入口

**大白话作用：** 用户配置一次就能自动上传，也能通过一条命令预览或补发已有记录。

依赖：TDX-05。入口：instrumentation、CLI、示例；对应 EXP-05 收尾。

实施要求：

- instrument() 和 initInstrumentation() 接受可选 exporter 接口；本地提交并确认写入状态后触发后台处理，成功和失败 run 均覆盖。
- run 返回前至少处理交付意图的可靠登记；不等待远端成功。登记失败走安全诊断，保持原业务返回值或原始异常。
- 后台工作有并发/容量上限，异常有人处理；导出在 suppression 上下文运行。明确共享 exporter 由谁关闭，避免一个 controller 关闭其他 controller 的资源。
- CLI 提供下列计划入口；这些命令在本任务完成前仍是目标 API：

```sh
alsnap export-otel <snapshot-directory> --config <config-file> --dry-run --json
alsnap export-otel <snapshot-directory> --config <config-file> --json
alsnap export-otel --resume --config <config-file> --json
```

- resume 恢复配置所指定队列及其已登记交付意图，不推导额外历史目录。显式导出导入快照可用，导入操作本身不触发自动转发。
- 第一版可复用现有退出码：0 为全部拟发送批次确认接受（可附警告）或成功 dry-run；1 为参数/配置/交付未完成；2 为源快照无效。零有效 span 要有 no_data 诊断，不能声称完成有效上传。
- 输出区分源快照、映射损失、已接受、待发、拒绝和未知送达；排队成功不等同于远端接受，HTTP 接受不等同于 UI 已显示。
- 提供通用包装、SDK 自动采集、历史快照与重启补传示例；均可使用本地 fixture，无真实生产数据。

验收：SDK 业务成功/失败结果保持原样；网络故障不重跑业务；命令 dry-run 无副作用、resume 范围受控、退出码稳定；并发 run、提前退出和共享 exporter 有回归。

### TDX-07：真实 Collector 验收、文档与打包

**大白话作用：** 让真正的接收程序检查数据，确保不只是我们自己的测试认为成功。

依赖：TDX-06。对应 EXP-06。

实施要求：

- 固定 Collector 发行版本/镜像摘要，提交最小 OTLP HTTP JSON receiver 与可核查 debug/file exporter 配置。保存可复现命令和脱敏 fixture。
- 验证工具重试、模型失败、并行、多父 links、来源/完整度、时间、拆批、出站内容和恢复。断言 Collector 解码后的状态，不能只检查 HTTP 200。
- 故障测试使用本地服务；多进程队列测试与真实 Collector E2E 分层执行，失败能判断属于映射、存储、网络还是平台。
- 首版兼容指南保留原计划的 Langtrace、Grafana，并补充 Langfuse/Phoenix 的官方接入依据。每个平台标记：文档核对、本地接收验证、平台界面实测；不将一项冒充另一项。
- 无云凭据不阻塞本地交付；未测试的平台功能明确标注。云端试传只用明确授权的环境和数据。
- 更新 README、原采集/导出计划、handoff、CHANGELOG；保留 ALS-204 延期/独立交付状态，不把旧 M4/M5 继续写成待开发。
- 更新 workspace、锁文件、tarball 白名单与临时消费者 smoke，加入 otel-export 的安装、CLI 和恢复验证。

验收：阶段 A 的组件测试、真实 Collector E2E、根质量门禁和 release:verify 均通过；完整检查退出码。环境缺依赖时报告具体阻塞及可执行复现命令，不能标成 E2E 已通过。

## 6. 阶段 B：本地只读 Viewer

### TDX-08：交付 ALS-204 本地查看界面

**大白话作用：** 点开任务就能看过程、失败位置和前后状态，不用逐行翻 JSON 文件。

依赖：现有 Trace Loader、Graph 和执行资格元数据；不依赖 TDX-05/06。可行性：高，但属于独立前端交付。

实施要求：

- 在现有仓库内建设本地 Viewer，复用读取与图投影逻辑；可增加 viewer 包和明确的 CLI 启动入口，先冻结最小读取 API。
- 默认仅监听 loopback；只访问用户明确选择的 Snapshot 根目录。校验路径、常规文件、内容大小和符号链接边界；处理 DNS rebinding/跨站访问，绑定 Host/Origin 或本地会话令牌。
- 页面包含：任务列表、来源/完整度/回放资格、时间线、调用图、失败筛选、节点摘要、输入输出、状态差异、checkpoint 和 artifact 信息。
- 区分未记录、被过滤、被截断和实际空内容；状态差异仅在具备可重建数据时显示，观察快照不填造状态。
- 大型 payload 和 artifact 按需读取；100k 事件使用分页/虚拟化/渐进图展开，不一次渲染所有节点。
- 不执行快照中的 HTML、脚本、工作流或外部链接请求；SVG/HTML 等潜在可执行产物采用安全文本或隔离查看策略。
- 首版不提供执行回放按钮、上传按钮和凭据管理。可显示能力与受限原因，并展示已有回放结果。
- 所有查看端点只读；浏览界面不会改变源快照或触发业务副作用。

验收：用正常、失败重试、partial、OTLP 导入、损坏和 100k 事件样例进行浏览器验证；记录加载性能与内存基线；含脚本/路径/链接的测试数据不会执行或越界读取。交付启动说明及界面验证记录。

## 7. 阶段 C：按需求分批演进

### TDX-09：标准 GenAI 属性与流式信息汇总

**大白话作用：** 平台能认出模型名称、token 数和工具种类，用户可以比较耗时和用量。

依赖：TDX-01、TDX-02；目标平台验收复用 TDX-07。

- 固定官方语义约定版本，增加 profile/version 标记；保留本项目来源、完整度和映射损失信息。
- 基于真实数据映射 operation、provider、request/response model、输入/输出 token、工具名称、错误类型等。元数据允许列表与正文策略分别处理。
- 为供应商流事件增加有界汇总器，保留消费者驱动迭代、不预读、不重复请求、取消/提前结束/未消费语义。不能只依赖最后一个事件推断完整答案与 usage。
- 明确缺失 usage、累计值与增量值的区别，避免重复计数；成本无已验证价格来源时保持缺失。
- 需要时增加 Phoenix/OpenInference 或特定平台的可选映射；不污染公共 Snapshot 协议。

验收：真实 SDK 配合本地 fixture，覆盖非流式、流式正常、取消和 usage 缺失；一个实际验证的平台能正确识别模型/工具与用量，未知信息不伪造。

### TDX-10：标准配置、protobuf 与压缩

**大白话作用：** 用户更容易沿用现有平台配置，大批数据发送时占用更少带宽。

依赖：TDX-00、TDX-03、TDX-05、TDX-07。

- 支持标准 OTEL_EXPORTER_OTLP_* 配置。优先级写明：显式配置优先；其后为 traces 专用环境变量，再为通用变量；默认仍不在未启用导出时联网。
- 通用 endpoint 是基础地址，traces endpoint 是完整目标；按官方规则拼接，避免重复添加或漏掉 `/v1/traces`。
- 标准 headers 只在发送内存中解析，保持凭据不入队；目标路由身份与凭据轮换分开处理。
- 增加 HTTP protobuf 和 gzip，优先复用成熟官方编码/传输组件，保留本地快照与交付契约；列出 SDK 依赖与版本。
- 清楚区分内部队列格式与线上编码。切换编码、过滤或目标不能无提示改变既有批次语义。
- gRPC 在有明确后端需求时另行扩展，不作为本任务必须交付项。

验收：JSON/protobuf 对同一 fixture 表达相同语义；压缩开关、请求限额、配置优先级及 URL 拼接通过；Collector 实际解码成功。

### TDX-11：实时观测与跨服务关联

**大白话作用：** 长任务执行到一半就能查看进展，跨机器调用也能串成同一条过程记录。

依赖：TDX-05 至 TDX-07；建议完成 TDX-09 后实施。复杂度：高，必须先补设计 ADR。

- 创建 run/调用时就建立可传播的 trace/span 身份，接入已有 OTel context 与 W3C Trace Context；跨进程父关系不自动转成可执行业务依赖。
- 设计外部父 trace 与本地 run 的关联，支持保留 run_id；必要协议新增按兼容政策版本化，不重写旧快照身份。
- 已结束 span 在运行中批量发送，运行根 span 在实际结束时发送；进行中步骤的展示需单独定义，不能反复伪造结束 span。
- 实时导出与最终快照补传共享身份和交付进度。映射版本兼容、失效游标和未知送达有明确策略。
- 跨服务只传播必要上下文；不把任意 baggage、凭据和用户原文自动发给外部目标。
- 保持现有 provider 共存、抑制重复采集、业务取消和未 await 调用 drain 的契约。

验收：两个本地服务串起同一 trace；长任务结束前已完成子步骤可查看；实时发送后补传不在本地重复入队；崩溃场景保留 partial/unknown 事实。

### TDX-12：采样、保留期限与性能预算

**大白话作用：** 长期运行时控制硬盘、内存、网络与平台费用，同时保留真正需要排查的记录。

依赖：TDX-05/07；Viewer 优化可联合 TDX-08。实时采样策略需与 TDX-11 协调。

- 先测基线：采集额外耗时、写盘次数、峰值内存、队列增长、映射/拆批耗时和 100k 事件查看性能，再定同机回归阈值。
- 评估 Recorder 保留全部事件、按条 fsync、全快照映射和队列扫描成本；优化不得悄悄降低原有耐久性保证。批量刷盘必须明确最大可能丢失窗口。
- 配置快照容量/期限、发送队列预算、远端按整条 trace 的抽样或条件选择；明确哪些任务必须保留。
- 要保证失败/慢任务保留，应在已知结果后选择，或采用有界尾部采样。提前丢掉数据后不能再声称保证保留失败任务。
- 默认本地清理策略显式启用；提供预览和受控范围。清理以完整快照及其引用关系为单位，考虑共享 artifact 和未完成的交付意图。
- 发送容量不足时定义阻塞/拒绝/延后策略；优先保留本地源数据和可观测的诊断，不静默丢弃。

验收：有可重复基准与前后数据；到达预算时行为明确、无静默损坏；回放所需快照不会被随机删去部分事件；保留策略和采样不会冒充全量数据。

## 9. 验证与完成标准

### 9.1 故障验收矩阵

| 场景                             | 必须观察到的结果                         |
| -------------------------------- | ---------------------------------------- |
| 工具先失败后成功                 | 保留每次尝试及正确 wire 状态             |
| 正文含敏感值                     | 未授权正文不发；授权正文脱敏后才入队     |
| service/scope/错误文本含秘密     | 过滤生效，报告和临时文件同样不泄露       |
| 两个进程同时入队，另一个慢速发送 | 入队可继续，容量不越界，所有权不混淆     |
| 环境变量指向新地址/目标身份变化  | 旧批次不自动转发到新目标                 |
| 凭据暂缺                         | 可恢复配置阻塞，不删除未发送数据         |
| 收到全接受警告/部分拒绝          | 正确区分，partial success 不自动整批重发 |
| 请求可能已送达但没有回复         | 报告未知送达，重发可能重复可见           |
| 快照已提交、尚未入队时退出       | 已登记的导出范围可恢复，未授权历史不扫描 |
| 发完后尚未保存回执时退出         | 不谎称 exactly-once，恢复结果可追溯      |
| 预算、磁盘、队列达到上限         | 有限资源使用、明确状态、源快照仍可排查   |
| 应用本来有 OTel provider         | 不替换、不误关闭，不重复采集导出请求     |
| 打包后新目录安装运行             | 不依赖工作区隐式包或未打包文件           |

### 9.2 检查命令

组件开发时运行与修改相关的测试；阶段 A 收尾执行：

```sh
pnpm run check
pnpm run release:verify
git diff --check
```

TDX-07 必须新增有文档说明的 Collector E2E 命令并执行。若检查脚本已经包含其他检查，不为刷次数重复运行；修改后按影响范围重跑。工具链使用仓库约束的 Node/pnpm 版本，环境问题与代码失败分别报告。

完成不是“有实现文件”或“单元测试通过”，而是：用户入口可用、失败行为明确、敏感路径有回归、真实接收端可读、打包消费者可运行、文档与状态一致。

交付报告列出：完成任务、修改原因、实际验证命令与结果、未验证的兼容项、迁移影响和剩余任务。后续阶段没有实施时保持待办，不归入完成数量。
